# ADR-002 • Atomic reservations on the shared schedule

| Field | Value |
| --- | --- |
| Status | Proposed |
| Context | A selection may cover several courts and slots in one facility. One invalid or occupied slot must reject the entire selection. Only one competing request can hold the same court and time. Expiry blocks confirmation immediately and triggers release within the five-second target. In-person bookings and schedule blocks use the same schedule. Drivers: FR-09–FR-14, FR-21, FR-22, FR-25, FR-26, FR-29, FR-32, NFR-02, NFR-03 and ASR-G1/G2/G3/G5. |
| Decision | Use PostgreSQL READ COMMITTED transactions, row locks and a partial GiST exclusion constraint on active schedule_entry ranges. HOLD, BOOKING and BLOCK share this table. Lock courts and insert ranges in ascending court/time order. Confirm by changing HOLD entries to BOOKING in the same transaction; release and cancellation retain inactive history. |
| Alternatives considered | Pre-generated 30-minute court-slot rows are easy to lock but require regeneration when opening hours change. One occupied row per slot supports ordinary UNIQUE constraints but produces many rows for long blocks. Range entries with an exclusion constraint cover overlaps of different lengths; they require btree_gist and consistent lock ordering. |
| Consequences | The database is the final guard against overlap and partial writes. Services still validate ownership, opening hours, consecutive selections and time boundaries. Historic prices and affected notification items are snapshots. Performance and release-time targets require separate measurements. |
| Review and evidence | Schema validation: 29/29 checks reported by Trí. Concurrency and release timing require separate tests. The feasibility spike covers connectivity and price read/write. |
