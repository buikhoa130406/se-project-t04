# ADR-003 • Server-side role and ownership checks

| Field | Value |
| --- | --- |
| Status | Proposed |
| Context | Facility search is public and proceeding to booking requires sign-in. Players may view and cancel their own bookings. Owners manage facilities they created. Account passwords must be stored as hashes. Drivers: FR-01–FR-05, FR-16, FR-23, FR-24, FR-28, NFR-04, NFR-05, ASR-G4 and ASR-G9. |
| Decision | Document each public or authenticated operation. For protected operations, the server identifies the caller, checks the role and verifies ownership of the relevant facility or booking before reading or changing data. Display actions appropriate to the role and store only password hashes. |
| Alternatives considered | Repeat authentication and all access checks in each operation: independently implementable but repeats identity and role logic. Use shared authentication and role checks plus resource-specific ownership checks inside each business operation: this is the proposed structure. |
| Consequences | The API specifies which operations are public, which require sign-in and how access failures are returned. Stored relationships identify who owns each facility and booking. Review guest booking entry, a player opening their own or another player's booking, and an owner attempting to change another owner's facility. |
| Review and evidence | Authentication and ownership are specified in the API contract. Session handling and password-hash configuration require implementation validation. Issue #9 · Issue #10 · Issue #12 · PR #24 |
